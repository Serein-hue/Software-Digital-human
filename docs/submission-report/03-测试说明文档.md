## 0. 当前质量结论

截至 2026 年 7 月 14 日，项目的测试成熟度可概括为：**后端已有资产，执行状态不均；前端以构建检查为主；CI 尚未形成测试门禁。**

| 子系统 | 资产事实 | 当前执行状态 | 结论 |
|---|---|---|---|
| Frontend | `build`、`lint`，无正式测试脚本 | build 通过；lint 存在 1 处错误 | 可构建，尚未形成 UI 自动化 |
| Express backend | 12 个 Node 测试 | 10 通过 / 2 失败 | 有回归资产，需修复 analytics 断言/实现偏差 |
| business-api | 35 个 pytest 命名测试 | 收集阶段被 seed 语法错误阻断 | 资产较完整，但当前不可纳入门禁 |
| admin-api | 12 个 pytest 测试 | 12 通过 | 当前最稳定的自动化测试子系统 |
| demo-mock-service | 7 个 pytest 测试 | 7 通过 | 可稳定执行，尚未接入 CI |
| RAG | 1 个脚本式测试函数，含 5 个检查步骤 | 本地模型未缓存时无法离线执行 | 需建立固定 fixture / mock embedding |
| LipSync | 实现模块 + 手工测试脚本 | 缺少断言型回归用例 | 功能已实现，测试口径需补齐 |
| GitHub Actions | Pages 构建与部署 | 未运行 npm test / pytest / coverage | 当前无持续集成质量门禁 |

## 一、测试策略

### 1.1 分层测试模型

测试体系按“当前已有资产 + 后续完善目标”组织，不把尚未落地的测试层描述为已全面覆盖。

| 层级 | 当前能力 | 主要对象 | 目标 |
|---|---|---|---|
| L1 构建与静态检查 | 已具备 | TypeScript build、ESLint、Python 导入/语法 | 阻止不可构建代码进入主分支 |
| L2 单元/接口回归 | 部分具备 | Express、business-api、admin-api、demo service | 关键输入、边界与错误码可重复验证 |
| L3 跨服务集成 | 部分具备 | API → RAG → 数据库 → Fay | 依赖故障、降级与 trace_id 可追踪 |
| L4 验收/E2E | 以手工为主 | 游客旅程、管理后台、小程序、口型同步 | 形成可自动复现的核心路径 |
| L5 性能/安全/质量集 | 方案已设计 | RAG 延迟、接口吞吐、拒答率、越权负例 | 建立发布基线和趋势数据 |

### 1.2 工具与运行口径

| 检查对象 | 当前工具 | 是否自动化 | 是否进 CI |
|---|---|:---:|:---:|
| Frontend build / lint | TypeScript、Vite、ESLint | 是 | 仅 build/deploy |
| Express API | Node 内置 test runner | 是 | 否 |
| FastAPI 服务 | pytest + TestClient | 是 | 否 |
| RAG | Python 脚本式冒烟 | 部分 | 否 |
| 合同 smoke | Shell 脚本 / OpenAPI 资产 | 部分 | 否 |
| Web E2E | 暂无正式 Playwright/Cypress 套件 | 否 | 否 |
| 性能与覆盖率 | 尚未形成可复现基线 | 否 | 否 |

### 1.3 测试环境

| 环境 | 用途 | 说明 |
|---|---|---|
| 本地开发环境 | 构建、lint、子系统测试 | Windows 11 / PowerShell；命令需使用 Windows 可执行语法 |
| 服务内 TestClient 环境 | FastAPI 路由与数据库集成 | 通过 pytest fixture 自举；当前部分服务仍受 seed/导入问题影响 |
| 完整联调环境 | API、RAG、Fay、Web 与小程序联调 | 需显式启动 8001/8002/5010/5000/10000/8765 等服务 |
| 公开演示环境 | GitHub Pages 静态前端 | 不包含 Python/RAG/Fay 后端，不能替代完整验收环境 |

### 1.4 已有测试资产与准确口径

| 测试文件/资产 | 命名测试数 | 类型 | 当前状态 |
|---|:---:|---|---|

| `business-api/tests/test_integration.py` | 27 | FastAPI 集成 | 被 seed 语法错误阻断 |
| `business-api/tests/test_health.py` | 8 | 健康与基础接口 | 与 business-api 同受收集阻断 |

### 2.1 测试用例编写规范

每个测试用例遵循统一模板：

| 字段 | 说明 |
|------|------|
| **TC-ID** | 测试用例唯一编号，格式：`{层级}-{模块}-{序号}` |
| **测试名称** | 清晰描述测试场景 |
| **前置条件** | 执行前必须满足的条件 |
| **输入数据** | 测试输入（参数、请求体等） |
| **操作步骤** | 按顺序描述执行动作 |
| **预期结果** | 期望的系统行为/输出 |
| **实际结果** | **留空**（供评审/执行时填写） |

## 三、性能测试方案

### 3.1 测试场景

| 场景编号 | 场景名称 | 描述 | 测试目标 |
|----------|----------|------|----------|
| PT-01 | RAG 语义检索延迟 | 模拟多用户并发提交知识检索请求 | 95分位 ≤ 3秒 |
| PT-02 | 检索+LLM生成延迟 | 模拟多用户并发请求检索增强生成 | 95分位 ≤ 5秒 |
| PT-03 | 业务API吞吐量 | 模拟高并发景点列表/详情查询 | ≥ 100 req/s |
| PT-04 | 文档入库性能 | 测试不同大小文档的入库耗时 | ≤ 10秒/100KB |

### 3.2 测试方法

#### RAG 检索延迟（PT-01）

```bash
# 使用 locust 或 wrk 进行压力测试
# 模拟请求：
POST /api/v1/rag/query
Body: {"query": "灵山大佛有多高？", "top_k": 5}

# 并发参数
# - 起步：10 并发用户
# - 峰值：50 并发用户
# - 持续：3 分钟
# - 测量：平均/95分位/99分位 延迟
```

**可接受阈值**：

| 指标 | 阈值 | 触发动作 |
|------|------|----------|
| 95分位延迟 | ≤ 3.0 秒 | 若超标，检查 Embedding 推理时间（预期5-15ms）和 ChromaDB 查询时间 |
| 错误率 | ≤ 1% | 若超标，检查服务端错误日志 |
| 吞吐量 | ≥ 20 qps | 若偏低，考虑增加服务进程数 |

#### 业务API吞吐量（PT-03）

```bash
# 模拟请求：
GET /v1/spots?page=1&page_size=20
GET /v1/spots/LS-001
GET /v1/routes

# 并发参数
# - 起步：50 并发用户
# - 峰值：200 并发用户
# - 持续：5 分钟

# 测量指标：
# - 平均延迟
# - 95分位延迟
# - 吞吐量 (req/s)
# - 错误率
```

**可接受阈值**：

| 指标 | 阈值 |
|------|------|
| 平均延迟 | ≤ 200ms |
| 95分位延迟 | ≤ 500ms |
| 吞吐量 | ≥ 100 req/s |
| 错误率 | ≤ 0.1% |

### 3.3 测试工具

## 四、缺陷管理

### 4.1 缺陷严重等级

| 等级 | 标签 | 描述 | 处理时限 | 举例 |
|:----:|------|------|:--------:|------|
| P0 | 致命 | 系统无法启动、核心功能完全不可用、数据丢失 | 立即修复 | 数字人无法启动、RAG 服务 500 |
| P1 | 严重 | 主要功能故障、关键业务路径中断 | ≤ 4小时 | 景点详情接口返回空数据、鉴权失效 |
| P2 | 一般 | 功能可用但行为异常 | ≤ 24小时 | 分页总数不准确、动画卡顿 |
| P3 | 轻微 | 表面问题，不影响功能 | ≤ 72小时 | 文案错别字、样式偏移、图标不统一 |
